# E2E interaction — when an E2E scenario freezes, and what to do when it fills a gap

> **Single source.** `create-exec-plan` (Q3d), `start-feature` (Step 2) and `run-exec-plan`
> (Step 0b / 0c / 1b / 3a) all apply **this** file. Do not restate the freeze point or the
> complement-detection branches inline in a skill — reference this file, so the call sites cannot
> drift apart.

## Why this exists

It is tempting to treat the chain ゴール像 → `E2E-NNN` → `[E2E]` AC as a one-way derivation:
requirements first, the E2E scenario derived from them, the plan derived from both. That premise
does not hold. An E2E scenario asks "is the thing we defined actually the
right end state?", and answering it changes the requirements as often as it follows them — a tool
that improves a business flow changes the flow it was specified against. When requirements are
written loosely, the E2E scenario is where the finished picture gets worked out. **Which document
was written first cannot decide which one is right.**

Two things follow, and they pull in opposite directions:

- Before implementation, the E2E scenario, the US and the spec must be free to correct one another.
  A fixed direction there forbids the most useful thing E2E does — finding what the requirements
  missed.
- During implementation, the E2E scenario must **not** move. Red-first (INV-T02) transcribes the
  `[E2E]` test from it before any code exists; if the scenario can drift while the plan runs, the
  frozen expectation measures nothing.

So the question is not "which comes first" but **"when does it freeze"**. And the freedom before the
freeze has a hazard of its own: an E2E scenario that can fill gaps in the requirements can also
**decide what to build without anyone deciding it**. This file fixes the freeze point and turns gap
filling into a detection — something a human resolves — rather than a silent path around the outer
gate.

## The freeze point

> **An `E2E-NNN` scenario freezes for a plan at the moment that plan — an exec-plan whose
> `## Sources` names the scenario as a source — is finalized.**

| | Before the freeze | After the freeze |
|---|---|---|
| **Relationship** | No direction. The scenario, the US and the spec may each be revised to match the others; none outranks another for having been written first | Directed: scenario → `[E2E]` test (red-first) → implementation → re-anchor back to the scenario |
| **A difference between them** | Ordinary authoring work — resolve it by editing whichever document is wrong | **A disagreement between frozen documents** — outer gate (CLAUDE.md「自律実装ループ」). The unattended loop halts with (a); a human chooses |
| **Editing the scenario** | Free | Only as a spec change through CLAUDE.md「仕様バージョンの管理」: an in-version fix (`main`) recorded in the frozen plan's Decision Log — or, if that plan is already completed, re-opened in a reconcile plan — or a next-version change on `spec/<label>` |

**"Finalized"** means the plan file has passed `create-exec-plan` (its Q3c readiness check cleared
and the file written). For a reconcile plan generated by `promote-spec` Step 7, it is the moment Step 7
creates the file — the human's approval of the promotion (Step 5) covers it, and no later acceptance
step exists. Such a plan never passes Q3d, so its first comparison happens **after** the freeze, at
`start-feature` Step 2 or `run-exec-plan` Step 0b; a gap or contradiction found there is handled like
any other (present / HALT (a)). A plan that never passed `create-exec-plan` — hand-written, or predating this
file — freezes when it is placed in `exec-plans/active/`; like a reconcile plan, its first comparison
comes after the freeze. In every case the plan's `created:` date is the record of the freeze; nothing
else needs to be stamped.

**The freeze is per plan.** A scenario that plan A names is frozen for plan A and still free for any
plan not yet written. Editing it is free *of plan B's constraints* only — it still changes plan A's
target, which is why the edit goes through the routing above and not around it. To find the plans a
scenario is frozen for, search the `## Sources` tables of `exec-plans/active/` **and**
`exec-plans/completed/` for its ID
(`grep -rn "E2E-001" exec-plans/active/ exec-plans/completed/ 2>/dev/null || true`). The grep also
matches Decision Log and Progress Log prose; only a hit inside a `## Sources` row counts. A hit in
`active/` is recorded in that plan's Decision Log; a hit in `completed/` is re-opened in a reconcile
plan — the two branches of the table above. Nothing detects an edit to a scenario
that leaves every AC line unchanged — the `gc` spec-drift backstop is keyed on AC-IDs — so this search
is the editor's job (see「Known gaps」).

**What this file does not change.** It fixes which document may correct which, and when that stops.
It does **not** change the *authoring order*: `create-spec` drafts the scenarios from an approved US
goal image and halts without one. Nor does it change where scenarios live: they are the spec's
`## E2E シナリオ` section (`docs/02_spec/**` § `E2E-NNN`).

## Complement detection — when the scenario says something the US and spec do not

At the sites below, compare the scenario's 前提, steps and 完了条件 against a **bounded set of frozen
sources** — the comparison set:

| # | In the comparison set | Why |
|---|-----------------------|-----|
| 1 | The US and spec sections the plan's `## Sources` row names, other than the scenario itself (for an `[E2E]` AC: the US `## ゴール像`／主要ユーザージャーニー) | What the plan already says the scenario condenses |
| 2 | That US's `## ゴール像` in full — including 非ゴール | A 非ゴール is where a contradiction is most visible |
| 3 | For **every AC the scenario lists under `満たす AC`**: its US `### AC-NNN` section **and** the spec section marked "satisfies AC-NNN" | Where a scenario step is most often stated. Without the US sections, a step another AC describes looks like a gap; without the spec sections, so does a UI-level step only the behavior section describes |

"Stated" means **stated somewhere in this set**, and nothing outside it is searched. The set is the
limit on purpose: an unattended driver needs a search it can finish, and every member is frozen
source material the plan already points at. An outcome that the set does not contain but some *other*
AC does is still a gap here — usually one the scenario's `満たす AC` list should name. Adding that AC
to the list edits the scenario, so it is still the human's call (① or ②), not the driver's.

Take the verdict from this table:

| The scenario, relative to the US / spec | What it is | Action |
|-----------------------------------------|-----------|--------|
| **Refinement** — the same journey or outcome the US / spec states, with concrete preconditions, steps or end state | Not a complement. This is what a scenario is for | Use it as written |
| **An outcome stated nowhere in the comparison set** — a step, a result or a 完了条件 that nothing in the comparison set describes | **A detected requirements gap.** The scenario is deciding something nobody decided | A human chooses one of: **① promote** it into the US / spec, landing it **inside the comparison set** — the US ゴール像, or the US / spec section of an AC the scenario lists under `満たす AC` (a promotion written as a new AC also adds that AC to `満たす AC`, which edits the scenario); promoted anywhere else, the next comparison finds the same gap. A spec change — routed per CLAUDE.md「変更のルーティング」, and see「Where the fix lands」 below; **② drop** it from the scenario; **③ the requirements are thin** — the gap is a symptom, and the US is reworked (`create-requirements`) before the plan proceeds. Unattended: **HALT (a)** |
| **A contradiction** — the same outcome, with a different expected result, or a result the US lists under 非ゴール | Frozen documents disagree | A human decides which is the target, and **the other document is then edited to agree** — by the human, as a spec change routed per CLAUDE.md「変更のルーティング」. Unattended: **HALT (a)**; the driver edits **neither** document |
| **No source** — the row names no `E2E-NNN` (`n/a（理由）`, or the plan has no `## Sources`) | Nothing to compare | Continue. The row's own `n/a（理由）` is the record — no separate line is needed |

**Scope the comparison to whether the outcome is stated in the comparison set**, not to whether
*this plan* covers it. A scenario step that a `満たす AC` entry outside this plan describes is
stated — not a gap. (This is scoped for the same reason as the
re-anchor in `run-exec-plan` Step 3a — a scenario always describes more than one plan — though not
identically: Step 3a ignores every AC outside the plan, while this comparison still reports an
outcome that only an AC outside `満たす AC` states.)

**Why a contradiction must end in an edit.** Recording "the US is the target" without changing the
scenario leaves both documents saying what they said. The comparison reads documents, not decisions,
so the next run — and every resumed run — finds the same contradiction and halts again: a state that
cannot be left. The decision is only complete once the document that lost has been corrected. (A
detected gap ends the same way: ① edits the US / spec, ② the scenario, ③ the requirements.)

**Why the second row halts instead of proceeding.** The scenario filling a gap is the mechanism this
file exists to keep — it is how loose requirements get found. But a filled gap that nobody looks at
has become a requirement no human set, and the `[E2E]` test transcribed from it would freeze that
requirement as the run's reference signal. The halt turns the complement into a **discovery**: the
gap is surfaced and a human decides what it means. Same family as `ac-sources.md`'s "a separate
outcome → HALT (a)", one level up — there the source says more than the AC line; here the scenario
says more than the requirements.

**Where the fix lands.** The comparison reads the documents on `main` — the current target the plan
is frozen against. A resolution therefore lets *this* plan proceed only once its edit is on `main`:

| Resolution | Routed to | What this plan does |
|-----------|-----------|---------------------|
| ①, ② or ③ as an in-version fix | `main` | Proceeds once the edit is merged; the next comparison passes |
| ① or ③ judged a **next-version** change | `spec/<label>` | The gap is still on `main`, so the next comparison halts on it again. The human also chooses one of: apply **②** on `main` now (drop the outcome from the current scenario; the next version adds it back), or **defer** this plan until the promotion (record `deferred` in its Decision Log) |
| A contradiction's edit | `main` only | Correcting a contradiction is fixing the current version (CLAUDE.md「変更のルーティング」: 矛盾の是正), never a next-version change |

**Why ① and ③ are different.** ① says the scenario is right and the requirements merely omitted it:
copy the outcome up. ③ says the omission is not isolated — the US is under-specified, and promoting
one step would paper over the rest. Both end in a requirements edit; they differ in how much is
reopened, which is exactly the judgement only a human can make.

## Where this is applied

The rule applies only where a scenario is **already read as a source** today. Extending it to other
sites — `doc-review`, `gc`, or a symmetric DOC-INV-006 that flags scenario steps with no US / spec
counterpart — would add new warnings, and **how far to extend the halt is an open decision**
that this file does not make. Until it is made, those sites do not apply this file.

| Call site | When | Action on a gap or a contradiction |
|-----------|------|-----------------------------------|
| `create-exec-plan` (Q3d) | Writing a `## Sources` row that names an `E2E-NNN` — the last moment before the freeze | Run the comparison with the user and **resolve it before the plan is finalized**: ① / ② / ③ for a gap, a choice of target (and the edit that follows) for a contradiction. Record the result (format below). Freezing an unresolved gap would freeze a decision nobody made. If the readiness check (Q3c) that follows rewrites an AC or a row so that it names a different `E2E-NNN`, compare that scenario too before finalizing |
| `start-feature` (Step 2) | Manual implementation path, loading the sources | Present the finding to the user and let them choose (① / ② / ③, or the target). Record the decision in the plan's **Decision Log** (format below) — ① and a contradiction's edit are spec changes, and CLAUDE.md requires their routing to be recorded there |
| `run-exec-plan` (Step 0b) | Before the loop, while opening every unchecked AC's sources for `R2` | **HALT (a)** before the loop starts — the same reason readiness runs up front: spend the human's attention once, before any test is frozen from the scenario |
| `run-exec-plan` (Step 0c / Step 1b / Step 3a) | Transcribing the `[E2E]` test, reading an AC's sources, re-anchoring | Backstop for what Step 0b missed: **HALT (a)**. Do not transcribe the gap into a test, and do not edit the scenario, the US or the spec. At Step 1b / 3a the `[E2E]` test may already hold the gap — see「Known gaps」 |

`create-spec` points here too, but not as a call site: it drafts scenarios **before** any freeze,
when correcting the US or the scenario is ordinary authoring. A gap it notices while drafting goes
into its report, the same way it already reports an AC that belongs to no scenario.

Same split as everywhere in DocDD: reading and comparing is execution; deciding what a gap means is
governance. Where a human is present it is a conversation; where none is, the only correct move is to
stop.

**A plan with no record** (it predates this file, or was hand-written) is not a halt by itself. The
record is evidence that `create-exec-plan` ran the comparison; its absence only means the comparison
has not been done yet, and `run-exec-plan` Step 0b does it.

## Known gaps

Two states this file does not yet close. They are written here so a reader meeting one knows it is
known, and what the existing rules already say about it.

| State | What happens today | What already applies |
|-------|--------------------|---------------------|
| **A promotion rewrites a frozen scenario.** `promote-spec` Step 4 finds in-flight collisions by AC-ID, so a promotion that changes an `E2E-NNN`'s steps or 完了条件 while leaving every AC line alone reports none — and silently moves the target of an active plan whose `[E2E]` test is already frozen | Not detected by `promote-spec` or by `gc` (whose spec-drift backstop is also keyed on AC-IDs) | 「The freeze is per plan」: whoever edits a scenario — a promotion included — searches `exec-plans/active/` and `exec-plans/completed/` for its ID, as that section describes. The person running `promote-spec` is that editor |
| **The gap is already in a frozen `[E2E]` test.** Step 0c transcribes the whole scenario before the loop. If complement detection first fires at Step 1b / 3a — or at Step 0b of a **resumed** run whose Step 0c test already exists (a plan predating this file, or a scenario edited between sessions) — the gap may already be the test's expected result, and the human's ② (drop it) or a contradiction resolved against the scenario changes a frozen expectation | Step 0c's resume rule ("an earlier session placed it → re-run, do not rewrite") would steer the run toward the dropped step | That change is **stop condition (c)** — a test expectation change grounded in a spec change (INV-T01 / INV-T02). The human records the spec change and the test change together in the Decision Log; the driver does not rewrite the test itself. Step 0b running before Step 0c is what keeps this rare on a first run |

Closing them — an `E2E-NNN`-keyed collision check in `promote-spec`, an E2E-keyed `gc` backstop — adds
detections — the same open decision as extending the call sites (「Where this is applied」).

## Record format

In the plan's `## Decision Log`, at `create-exec-plan` (and wherever a human resolves a finding):

```markdown
- E2E 凍結: `E2E-001`（`docs/02_spec/app_spec.md`）をこのプランの起点として凍結（プラン確定 YYYY-MM-DD）。
  補完検出: comparison set（行の起点・`US-003` § ゴール像 全体・`満たす AC` 各 AC の US/spec 節）と照合 → 詳細化のみ。
```

or, when a finding was resolved:

```markdown
  補完検出: 要件の穴 1 件 — 「{シナリオが述べ、US/spec に無い成果}」→ 人の決定: ①昇格（{comparison set 内の節} に追記、
  ルーティング: {main | spec/<label> ＋ main で②適用 | spec/<label> ＋ このプランを deferred}）| ②シナリオから削除 | ③要件の見直し（{何を}）。
  補完検出: 矛盾 1 件 — 「{シナリオの記述}」と {US/spec の節} の「{記述}」→ 人の決定: {どちら} を正とし、
  {もう一方の文書と節} を修正（ルーティング: main — 矛盾の是正）。
```

When `run-exec-plan` halts on it, the HALT entry names the scenario, the phrase, and the row:

```markdown
- HALT at AC-NNN (stop condition a). 補完検出: `E2E-001` の「{phrase}」が comparison set
  （行の起点・`US-003` § ゴール像 全体・`満たす AC` 各 AC の US/spec 節）のどこにも無い（要件の穴）。人の決定: ①昇格 ②削除 ③要件の見直し のいずれか。
```

## Relationship to the other checks

| Check | The question it asks |
|-------|----------------------|
| AC readiness (`../create-exec-plan/ac-readiness.md`, R1–R5) | Can this criterion be measured at all? |
| Red-first (`../run-tests/red-first.md`, INV-T02) | Is the measurement independent of the implementation? |
| AC sources (`../create-exec-plan/ac-sources.md`) | Does the implementer receive the whole goal — and is the result checked against it? |
| `[E2E]` coverage | Do the fragments add up to something the user can do? |
| **E2E interaction** (this file) | Is the scenario the run steers toward one a human decided — and does it hold still while the run steers toward it? |

`ac-sources.md` compares a source against the **AC line**. This file compares the scenario against
the **requirements** it sits beside. A scenario can refine its `[E2E]` AC line perfectly and still
state an outcome no requirement contains; neither check finds what the other does.
