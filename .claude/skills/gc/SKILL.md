# Skill: Garbage Collection

> **When to run**:
> - Weekly (e.g., every Monday on a regular schedule)
> - After a large feature merge
> - When documentation and implementation are suspected to have drifted
>
> **Purpose**: Periodically resolve drift in code and documentation generated by agents,
> and continuously maintain the health of the repository.
>
> **Estimated time**: Varies with repository size; target completion within 30 minutes per run.

---

## What this skill does

Runs the following steps in order.

```
① Document freshness scan (all documents)
② Architecture drift detection (all files)
③ Document invariant check (all documents)
④ Document lifecycle cleanup
⑤ CONTEXT.md update
⑥ GC report generation
```

---

## Steps

### ① Document freshness scan (check-doc-freshness full-scan mode)

Run the `check-doc-freshness` skill against the entire repository.

- Target: all documents in `docs/**/*.md` that have a `tracks:` field
- Load code files matching the `tracks:` patterns and verify for discrepancies
- Fix any discrepancies found

**Also check:**
- For documents that do not have a `tracks:` field, determine whether one should be added
  - Add `tracks:` to documents that have a 1:1 correspondence with code
  - Skip if not necessary

### ② Architecture drift detection (check-invariants full-scan mode)

Run the `check-invariants` skill against all of `src/**`.

- Check all files corresponding to every INV in `invariants.md`
- Fix any violations found
- If there are many "warning"-level violations, consider revising the conditions in `invariants.md`

### ③ Document invariant check (check-doc-invariants full-scan mode)

Run the `check-doc-invariants` skill against all documents in the repository.

- Target: all `docs/**/*.md` and `exec-plans/**/*.md`, plus the wider ranges the skill defines
  for its script-backed invariants (the convention documents themselves, and active plans'
  `## Sources` tables)
- Check every built-in invariant the skill defines. The list is the skill's, not this file's, so a
  new invariant needs no edit here; that skill runs the script behind the mechanical ones, this file
  does not invoke it directly
- Fix any violations found — **except DOC-INV-012**. A `## Sources` row that cannot be opened is
  reported to a human, not repaired: repointing it to the file it "probably meant", or writing
  `n/a` in its place, is a decision about what that AC condenses
  (`create-exec-plan/ac-sources.md`「When a source cannot be opened」)
- Do **not** pass `--base` (that is `pre-pr` ③'s PR mode). Without it every DOC-INV-012 ❌ is an ❌
  here, whichever plan it is in — this full scan is the **backstop** for the rows a PR listed under
  "In other plans — not blocking this PR" (`check-doc-invariants`「Which ❌ blocks which run」).
  Name the plan of each DOC-INV-012 row in the report so its owner can be told — a full scan
  cannot tell which of them some PR listed apart, and does not need to
- For a DOC-INV-001 or DOC-INV-003 hit involving a research note (`docs/00_project/research/`) — a
  note linking below layer 0, or a document linking to a deprecated note: the only fix is to turn the
  link into the **same** path in backticks, which changes no meaning
  (`../init-project/research-note-format.md`「Rechecking」, what may change). **Never repoint** it to
  another document, in particular not to a deprecated note's successor: that would silently change
  which observation a decision rests on. A link to a deprecated note stays reported by the research-note backstop below
  until the human records what it means
- For DOC-INV-005 warnings: use context to decide whether Mermaid conversion is worthwhile;
  record the decision if leaving ASCII art intentionally. In a research note, report it and do not
  convert: a note is not rewritten (`../init-project/research-note-format.md`「Rechecking」)
- For the DOC-INV-006 migration warning (scenarios still in a spec's `## E2E シナリオ` section):
  **report it, do not move them**. Moving a scenario breaks every active plan's `## Sources` row
  that names it, and repointing those rows is a human's call — the same reason DOC-INV-012 is not
  repaired here. The move itself is described under DOC-INV-006 in `check-doc-invariants`
- For the DOC-INV-006 **symmetric check** (要決定 / 要確認 / ℹ️) and the upward-trace lines
  (`由来ジャーニー` / `満たす業務要求`): **report them, do not fix them** — not even an ❌ that names
  a missing US. Dropping a scenario step, promoting it into the US, choosing which side of a
  contradiction is right, or deciding which journey a scenario realizes is each a decision about
  what to build; "fix any violations" above does not reach it
  (`create-spec/e2e-interaction.md`「Where this is applied」)

### ④ Document lifecycle cleanup

Review the status of each document according to the following `status:` transition rules.

| Transition | Trigger |
|------------|---------|
| (new) → `draft` | On file creation |
| `draft` → `active` | On PR merge, or when reviewed within 7 days of creation |
| `active` → `deprecated` | When the corresponding code/feature is deleted, or when a successor document becomes `active` — except a research note, which is deprecated only by a recheck that found a change ([`../init-project/research-note-format.md`](../init-project/research-note-format.md)「Rechecking」) |
| `deprecated` → (deleted) | Can be deleted 30 days after becoming `deprecated` — except a research note under `docs/00_project/research/`, which is kept: the superseded decisions still name it ([`research-note-format.md`](../init-project/research-note-format.md)「Rechecking」) |


| Check item | Criteria | Action |
|-----------|----------|--------|
| `draft` older than 7 days | Determined from `created:` date | Update to `active`, or continue with a recorded reason |
| `active` but corresponding code deleted | `tracks:` files do not exist | Change to `deprecated` |
| `deprecated` older than 30 days | Determined from `status: deprecated` date | Delete (or prompt for confirmation) — never a research note (`docs/00_project/research/`) |
| All acceptance criteria in `exec-plans/active/` are complete | Review checklist | Suggest running `complete-exec-plan` |

**Spec-drift backstop (in-version stale):**

Detects already-shipped ACs whose defining spec changed *after* completion but were never
re-opened for reconciliation (the safety net for the procedure in CLAUDE.md
"現バージョン修正による stale の扱い"). Results are **candidates requiring human confirmation**,
not definitive stale flags — the timestamp signal is heuristic (see caveats in step 3).

1. For each `exec-plans/completed/*.md`, read its `completed:` date and the AC-IDs it delivered
   (`^- \[[ x]\] AC-NNN:` lines).
2. For each delivered AC-ID, find its **defining US** by reverse lookup — the
   `docs/01_requirements/user_stories/US-*.md` whose `ac_ids:` contains that AC-ID. (DOC-INV-004
   enforces this traceability for `active/` plans only — *not* `completed/` — so for a shipped AC the
   US is usually present but not guaranteed.) Anchor the staleness check on the **US** (which defines
   the AC); the AC's code is reached via the US's — or its linked design doc's — `tracks:`. Do **not**
   assume a single doc carries both `ac_ids:` and `tracks:`.
   - **If no defining US is found**, that absence is itself a drift signal — the AC was likely
     removed or renamed by a later in-version correction (a REMOVED-AC case). Flag it as an
     untracked-drift candidate and recommend reconcile/deprecation per CLAUDE.md
     "現バージョン修正による stale の扱い", rather than assuming the lookup cannot fail.
3. Decide whether **this AC's spec actually moved** after completion — not merely any edit to the file:
   ```bash
   git log --follow --format=%h -- <US path>   # commits touching the US, following renames
   git show <commit> -- <US path>              # confirm THIS AC's ### AC-NNN block changed
   ```
   This is a heuristic, so apply these caveats to avoid false flags:
   - Use `--follow`, or a renamed/moved US loses its history and never flags (false negative).
   - `completed:` is a `YYYY-MM-DD` date (no time): a same-day edit is ambiguous — treat as a candidate.
   - A whole-file timestamp also moves on typo fixes or edits to a *different* AC in the same US, so
     confirm the specific `### AC-NNN` block actually changed before flagging (false positive).
4. Check whether the AC is already tracked or was intentionally deferred:
   ```bash
   grep -rlE "^- \[[ x]\] AC-NNN:" exec-plans/active/ 2>/dev/null   # already re-opened?
   ```
   - An **open reconcile/active plan** re-opens the AC-ID → tracked, no action.
   - An **acknowledgement marker** for the AC (a Decision Log line `reconcile: deferred` or
     `reconcile: n/a` in the relevant active plan) → a deliberate decision not to reconcile yet;
     suppress, do not re-flag.
   - Otherwise → flag as **untracked spec drift (candidate)**: recommend re-opening the AC in a
     reconcile plan per the CLAUDE.md procedure. Do not auto-create — reconciliation scope is a
     human/agent decision.

**E2E backstop (keyed on `E2E-NNN`):**

The spec-drift backstop above is keyed on AC-IDs, so it cannot see two states of an E2E scenario:
one that no plan ever took up, and one edited after a plan froze it while every AC line stayed the
same. Both are found here by matching the scenarios against the plans' `## Sources` tables — the
same rows `create-spec/e2e-interaction.md` uses to decide which plans a scenario is frozen for.
Results are **candidates for a human**, never auto-filed, like the backstop above.

**There is no ledger file.** Which scenario each plan took up is derived on every run from the
scenario files and the `## Sources` rows of `exec-plans/active/` and `exec-plans/completed/`. A
hand-kept index (`E2E-NNN → plan`) would be a second copy that nothing forces anyone to update —
the reason CLAUDE.md gives for not keeping a separate Spec Drift Log: it goes unscanned and stale.

1. **Collect the scenarios and what names them.** Scenarios: each `docs/01-02_e2e/E2E-*.md`, and
   each `### E2E-NNN:` block in a spec's old-layout `## E2E シナリオ` section (a block takes the spec
   file's `status:`). Skip any whose `status:` is `draft` (not approved yet — no plan is expected to
   take it up) or `deprecated` (retired — no plan should). What names them:
   - the `## Sources` rows of every plan that name an ID — the only thing that **freezes** a scenario
     (`create-spec/e2e-interaction.md`「The freeze point」);
   - in a plan with no `## Sources` table (it predates the convention), its `[E2E]` AC lines
     (`AC-005: [E2E] E2E-001 のとおり…`). These count as **taking the scenario up** — step 2 only.
     They do not freeze it, so step 3 (like `promote-spec`'s collision check) ignores them.

   The same ID in a Decision Log or a Progress Log is history, not a claim on the scenario:
   ```bash
   grep -rn "E2E-[0-9]\{3\}" exec-plans/active/ exec-plans/completed/ 2>/dev/null || true
   ```
2. **Unpicked scenario (candidate).** An approved scenario that nothing collected in step 1 names, in
   either directory. Every one of its ACs can go green in some plan while the through-flow it
   describes was never planned as a whole — what a per-plan `[E2E]` check cannot see. Report it; a
   scenario that is simply not planned *yet* is the common, harmless reading, which is why this is a
   weekly candidate and not a ⚠️ at every `pre-pr`.
3. **Scenario edited after a plan froze it (candidate).** For each scenario, take the plans whose
   `## Sources` row names it, each with its freeze date — the plan's `created:`, or for a row added
   later the date in its `E2E 凍結（後から追加 YYYY-MM-DD）` record (`e2e-interaction.md`). Find the
   changes to the scenario as they **landed on `main`**, after the earliest of those dates:
   ```bash
   git log main --first-parent --since="<freeze date> 00:00" --format="%h %cd" --date=short -- <scenario file>
   git diff <commit>^1 <commit> -- <scenario file>   # confirm 前提 / steps / 完了条件 / 満たす AC changed
   ```
   `--first-parent` dates each change by the commit that brought it onto `main` (a merge commit, a
   squash or a rebase-merge, in the PR flow), so a branch commit authored before the freeze but merged
   after it is not missed. A local fast-forward merge is the exception: it puts the branch's commits
   on the first-parent chain with their own, earlier dates.
   `00:00` matters: a bare date is filled in with the current time of day, which would drop the
   same-day changes this check means to keep. `%cd` is that commit's date, the one `--since`
   filters on. For a scenario renamed or moved (DOC-INV-006's migration), run it on the old path too.
   For an old-layout scenario the file is the spec file, so confirm that **this** `### E2E-NNN`
   block changed, not another part of the file. A change to the frontmatter alone, or a move with
   unchanged text, is not an edit to what a plan froze.

   Judge **each freezing plan** against the latest change after its own freeze date, then group the
   result into **one entry per scenario** that lists every plan left untracked:

   | The freezing plan is… | It is tracked when… | Otherwise |
   |-----------------------|---------------------|-----------|
   | **completed** | another plan — active or completed, a reconcile plan normally — names the scenario under an `[E2E]` AC in its `## Sources` and was frozen on or after the change (it verifies the new text); or a plan — active or completed — that froze the scenario before the change records the change in its Decision Log, dated on or after it (the in-flight owner that took it on, below — `promote-spec` Step 7's `E2E-NNN は <label> の昇格で変更` is such a record); or a plan — active or completed — has `reconcile: deferred — E2E-NNN` / `reconcile: n/a — E2E-NNN` recorded on or after the change | **Untracked E2E drift (candidate)** — recommend re-opening the `[E2E]` AC in a reconcile plan (CLAUDE.md「現バージョン修正による stale の扱い」) |
   | **active** | its Decision Log mentions the scenario's ID in an entry about the change, dated on or after it — its own `E2E 凍結` record does not count | **Unrecorded edit to a frozen scenario (candidate)** — the plan's target moved without a record; its owner records it and decides what it means for the frozen `[E2E]` test |

   **In-flight wins**, as in `promote-spec`'s precedence rule: when an active plan froze the scenario
   before the change, report the active plan's line, and do not recommend a reconcile plan for a
   completed one — the in-flight owner reconciles the flow. Its record of the change keeps the
   completed plan tracked even after the in-flight plan itself completes (the second clause of the
   table), so the precedence does not turn into a weekly candidate once the owner is done. A
   completed reconcile plan likewise keeps the original plan tracked: the "frozen on or after the change" test is what stops a drift that was
   already reconciled — and archived — from being raised again every week.

   **Same-day dates** (they carry no time) are resolved on purpose in two directions: a change on the
   day a plan froze the scenario counts as **after** the freeze (a candidate — a just-frozen scenario
   edited the same day is worth a look), while a plan frozen on the day of the change counts as
   **tracking** it (a reconcile plan created the day a promotion merged is the normal flow, not a
   gap).

   This is the safety net for the search `e2e-interaction.md` asks every editor of a scenario to make
   by hand. It does not replace that search — it finds the ones that were skipped, a week late.

**Research-note backstop (premises due for a recheck):**

Apply [`../init-project/research-note-format.md`](../init-project/research-note-format.md)「The `gc`
backstop」 (steps 1–6): research notes due for a recheck that a current decision cites, and current
decisions still resting on a deprecated note. Results are **candidates for a human**, like the
backstops above. **Do not edit** a note, its dates, or any citing document: whether the outside world
changed is found by looking at it, and what follows from a change is a routing decision (CLAUDE.md
「変更のルーティング」) — neither is this skill's.

- Verify and update the priority tasks to reflect the latest `exec-plans/active/`
